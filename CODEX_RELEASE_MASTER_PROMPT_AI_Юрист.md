Твоя задача — **не ограничиваться анализом, планом, scaffolding, псевдокодом или одной функцией**. Ты обязан последовательно реализовать весь утвержденный объем работ, двигаясь по контрольным точкам, пока:

Не спрашивай после каждого шага: «Продолжать?», «Что делать дальше?» или «Какой этап выбрать?». После завершения одной задачи самостоятельно бери следующую незавершенную задачу по плану и продолжай работу.

Останавливайся и запрашивай решение пользователя только в четырех случаях:

Во всех остальных случаях принимай разумное инженерное решение, документируй его в ADR и продолжай.

## 1. РЕЖИМ АВТОНОМНОЙ РАБОТЫ

Работай непрерывными вертикальными срезами: **данные → backend → AI/integration → mobile/admin UI → тесты → документация → commit**.

Нельзя считать задачу выполненной, если создан только экран без рабочей логики, только endpoint без клиента, только таблица без миграции, только интерфейс адаптера без тестового режима или только тест без реализации.

Применяй следующий цикл до полного release candidate:

1. Проверь состояние репозитория и текущую реализацию.
2. Определи первый незавершенный P0-пункт по плану и backlog.
3. Составь короткий внутренний план конкретного вертикального среза.
4. Реализуй его полностью.
5. Добавь обработку ошибок, безопасность, аудит и локализацию.
6. Обнови OpenAPI и типизированные клиенты, если изменился контракт.
7. Добавь unit, integration и при необходимости E2E-тесты.
8. Запусти линтеры, typecheck, тесты и доступные сборки.
9. Исправь все ошибки, вызванные изменением.
10. Обнови статус, доказательства проверки и документацию.
11. Сделай небольшой логичный Git-коммит.
12. Перейди к следующей незавершенной задаче без ожидания дополнительной команды.

Если приближается ограничение контекста или времени выполнения:

- не оставляй worktree в непонятном состоянии;
- заверши текущий атомарный срез либо безопасно откати только свои незавершенные локальные изменения;
- запусти доступные проверки;
- сделай коммит;
- создай или обнови `docs/project/CODEX_HANDOFF.md`;
- укажи выполненное, результаты тестов, открытые блокеры и точную следующую задачу;
- следующий запуск должен сначала прочитать `CODEX_HANDOFF.md` и автоматически продолжить с указанного места.

## 4. ЦЕЛЕВАЯ АРХИТЕКТУРА

Сохрани монорепозиторий и следующую базовую архитектуру, если ADR не докажет необходимость изменения:

```text
apps/mobile          Flutter Android/iOS
apps/admin           Next.js + TypeScript web panel
services/api         NestJS core API and integration gateway
services/ai          FastAPI AI orchestrator, RAG and validators
packages/contracts   OpenAPI and shared contracts
packages/*           reusable typed clients, schemas and UI tokens
infra                 local/staging/production infrastructure
 docs                 requirements, ADR, operations, testing and release
```

Обязательные технологии и принципы:

- Flutter с Riverpod и GoRouter;
- Next.js + TypeScript;
- NestJS + TypeScript;
- FastAPI + typed Python;
- PostgreSQL + pgvector;
- Redis для cache, locks, rate limits, queues и resumable jobs;
- S3-compatible storage, локально MinIO;
- фоновые задания через BullMQ/совместимую очередь;
- REST `/api/v1`, webhooks, idempotency keys;
- OpenAPI как контракт;
- структурированные логи, correlation ID, OpenTelemetry;
- Docker Compose локально;
- отдельные конфигурации dev/staging/prod;
- инфраструктура и способ production-deploy должны быть воспроизводимыми.

Не создавай распределенные микросервисы без необходимости. Сохраняй четкие модульные границы, но избегай лишней сложности. Бизнес-логика должна быть отделена от UI, ORM, внешних провайдеров и транспорта.

## 5. ОБЯЗАТЕЛЬНЫЕ ЭКРАНЫ И ДИЗАЙН MOBILE

### 5.1. Визуальный стиль

Реализуй интерфейс нативными Flutter-виджетами. Не вставляй готовые скриншоты как фон или вместо интерфейса.

Основная тема — **светлая премиальная тема для Казахстана**:

- фон: белый, теплый ivory, светло-бежевый;
- акценты: спокойное золото, без чрезмерного блеска;
- основной текст: темно-графитовый/темно-синий для достаточного контраста;
- карточки: белые, мягкая тень, тонкая бежевая/золотая граница;
- CTA: золотая кнопка с темным читаемым текстом;
- крупные touch targets не менее 44×44;
- понятные иконки;
- минимализм, простая иерархия, отсутствие визуального шума;
- корректная адаптация к маленьким экранам, SafeArea, Dynamic Type/text scale;
- WCAG-контраст: не использовать светло-золотой цвет для длинного текста на белом фоне;

- skeleton, loading, empty, offline, retry, disabled, success и error states для каждого асинхронного экрана.

Создай единый design system:

- semantic colors;
- typography;
- spacing scale;
- radii;
- elevations;
- icon sizing;
- buttons, inputs, chips, cards, dialogs, banners, progress steps;
- light/dark tokens;
- golden tests основных компонентов.

## 7. ЧАТ И ГОЛОСОВОЙ СЦЕНАРИЙ

Основной flow:

```text
голос/текст → transcript → пользовательская проверка → классификация → уточнения → RAG →
юридический ответ → голосовой ответ → дело → документы → следующий шаг
```

Реализуй:

- текстовые и голосовые сообщения;
- потоковую расшифровку;
- RU/KK/EN;
- ручное исправление текста;
- подсветку фрагментов с низкой уверенностью;
- запись до настраиваемого лимита;
- паузу/возобновление;
- сохранение незавершенной записи и текста при звонке, background, блокировке, падении и потере сети;
- продолжение в том же чате;
- автоматическое название чата;
- структурированное summary длинной истории;
- не отправлять в LLM всю историю, если достаточно summary + последние сообщения;
- TTS с play/pause/speed/replay;
- текст всегда сохраняется независимо от TTS;
- удаление исходного аудио после успешной транскрипции по умолчанию;
- сохранение аудио только при отдельном согласии;
- WebSocket/SSE для прогресса: `transcribing`, `classifying`, `retrieving_sources`, `validating`, `generating`, `review_required`, `ready`, `failed`.

## 8. AI-ОРКЕСТРАТОР И МАРШРУТИЗАЦИЯ МОДЕЛЕЙ

### 8.1. Общий принцип

Ни один конкретный model ID не должен быть зашит в бизнес-логику. Все провайдеры, модели, лимиты и цены задаются через env/config/admin settings.

Создай provider-neutral interfaces для:

- LLM;
- embeddings;
- STT;
- TTS;
- reranker;
- OCR/vision при необходимости.

### 8.2. Уровни сложности

Система автоматически определяет:

- `simple`;
- `medium`;
- `complex`;
- `human_review_required`.

`simple`:

- определение языка;
- извлечение Ф.И.О., ИИН/БИН, дат, сумм и реквизитов;
- категория/подкатегория;
- краткое резюме;
- перечень недостающих полей;
- простое объяснение уже найденной нормы;
- навигация и стандартные сообщения.

`medium`:

- анализ нескольких фактов и норм;
- основной план действий;
- стандартная консультация;
- досудебная претензия;
- стандартное заявление/иск;
- анализ нескольких документов.

`complex`:

- сложные договорные и строительные споры;
- большой пакет доказательств;
- противоречащие нормы;
- апелляционная/частная жалоба;
- пропущенные сроки;
- высокие суммы и высокий риск;
- сложная процессуальная стратегия;
- итоговая проверка сложного документа.

Маршрутизация учитывает не только длину запроса, но и:

- категорию;
- риск;
- число сторон;
- число документов;
- объем контекста;
- наличие процессуального срока;
- противоречия;
- качество транскрипции;
- уверенность;
- необходимость подписания/подачи.

Если уверенность недостаточна, автоматически повышай уровень модели. Высокорисковый финальный вывод нельзя оставлять только дешевой модели.

### 8.3. Учет стоимости

Сохраняй без персональных данных:

- provider;
- model alias/model ID из runtime config;
- input units;
- cached input units;
- output units;
- audio seconds;
- duration;
- estimated cost;
- complexity;
- risk;
- confidence;
- escalation reason;
- prompt version;
- user/case correlation identifiers;
- успех/ошибка.

В admin реализуй:

- цены моделей;
- budget per day/month;
- thresholds 70%, 85%, 100%;
- уведомления;
- hard limit/soft limit;
- optional automatic TTS disable при превышении бюджета;
- отчеты по модели, языку, категории и пользователю;
- kill switch провайдера.

## 9. ЮРИДИЧЕСКИЙ RAG И ЗАЩИТА ОТ ГАЛЛЮЦИНАЦИЙ

### 9.1. Официальные источники

Юридически значимый ответ формируется только на основании разрешенного официального индекса. Минимально предусмотри адаптеры для:

- `zan.gov.kz`;
- ИПС «Әділет»;
- официальных ресурсов судебных органов;
- официальных ресурсов государственных органов;
- нормативных постановлений Верховного Суда;
- официальных форм и разъяснений.

Не предполагай, что HTML-scraping разрешен. Используй только официальный документированный способ. При отсутствии такого способа создай ingestion interface, test fixture, manual/admin import и documented blocker.

### 9.2. Версионность источников

Для каждого акта/фрагмента храни:

- официальный идентификатор;
- полное название;
- тип;
- номер;
- орган;
- дату принятия;
- дату вступления в силу;
- дату изменения;
- статус;
- язык;
- статью/пункт/подпункт;
- source URL;
- retrieval timestamp;
- effective-from/effective-to;
- checksum/content hash;
- source version;
- embedding version.

### 9.3. Тройная проверка

Обязательная проверка нормы:

1. перед показом юридического ответа;
2. перед финальным формированием документа;
3. непосредственно перед подписанием/отправкой.

Citation Validator должен проверять:

- существование акта;
- существование статьи/пункта;
- принадлежность нормы акту;
- статус действия;
- применимую дату;
- отсутствие будущей редакции для текущего события;
- соответствие текста официальной редакции;
- официальный источник;
- связь процитированного фрагмента с выводом.

Если подтверждение не прошло, не показывай утверждение как подтвержденное. Возвращай машинный статус:

```json
{
  "status": "insufficient_authoritative_sources",
  "message": "В официальных источниках не найдено достаточного подтверждения для точного ответа.",
  "requiredAction": "clarify_or_human_review"
}
```

### 9.4. Безопасный формат ответа

Структурированный ответ должен включать:

1. как система поняла проблему;
2. юридически значимые факты;
3. недостающие сведения;
4. применимые подтвержденные нормы;
5. простое объяснение;
6. права пользователя;
7. обязанности;
8. риски;
9. сроки;
10. пошаговый план;
11. куда обращаться;
12. документы;
13. досудебный порядок;
14. государственную пошлину;
15. доказательства;
16. официальные источники и дату актуальности;
17. CTA формирования документа;
18. предупреждение/экспертную проверку.

Жестко запрещено:

- придумывать статью, норму, срок, орган или практику;
- использовать только память модели как юридический источник;
- выдавать проект НПА за действующую норму;
- выдавать отмененную норму как действующую;
- гарантировать результат;
- скрывать низкую уверенность.

### 9.5. Prompt injection

Недоверенными являются пользовательский текст, загруженный документ, OCR, web content и внешние webhook payloads.

Реализуй:

- отделение system policy от retrieved content;
- запрет исполнения инструкций из документов;
- tool allowlist;
- серверную проверку каждого tool call;
- content sanitization;
- ограничение URL/domain allowlist;
- контроль размера контекста;
- PII masking;
- audit rejected tool calls;
- тесты prompt injection и data exfiltration.

Планируемые слоты:

Если реальный API или разрешение отсутствует:

- реализуй interface;

- добавь блокер с перечнем необходимых данных;
- продолжай все независимые работы.

Запрещено:

- обход CAPTCHA;
- browser automation закрытого государственного кабинета;
- reverse engineering закрытого API;
- хранение логина/пароля eGov или Судебного кабинета;
- перехват SMS;
- хранение private EDS key/password;
- скрытая или массовая роботизированная подача.

### 15.1. WhatsApp/SMS/e-mail/почтовая отправка

WhatsApp — только официальный WhatsApp Business API/разрешенный provider. SMS/e-mail/почтовая отправка — через документированные API.

Показывай пользователю стоимость до подтверждения, если канал платный.

Технический статус `sent/delivered/read` не объявляй юридическим доказательством надлежащего вручения без подтвержденного правового основания.

### 15.2. Судебный кабинет

При официальном API реализуй:

- идентификацию;
- справочники;
- стороны и представителя;
- тип производства;
- суд;
- требования/цену иска;
- документы и приложения;
- сведения о пошлине;
- preview;
- подписание;
- явное подтверждение;
- idempotent submission;
- receipt;
- номер обращения/дела;
- статусы и причины возврата.

Без официального API реализуй только assisted mode:

- готовый пакет DOCX/PDF;
- перечень приложений;
- проверка полей;
- инструкция;
- разрешенный deep link/переход;
- ручной ввод номера обращения;
- прикрепление квитанции;
- напоминания.

Не называй assisted mode полной автоматической интеграцией.

### 15.3. Подписание

Flow:

1. backend формирует immutable content hash;
2. пользователь видит итоговую версию;
3. подтверждает данные, адресата и приложения;
4. выполняется handoff в официальный сервис;
5. пользователь сам подтверждает подпись;
6. backend получает проверяемый результат;
7. сохраняются hash, способ, время, результат и audit event.

- отсутствие duplicate submission при повторах/timeout.

### 19.5. Severity

Release запрещен при Blocking или Critical дефектах.

Blocking:

- приложение не запускается;
- вход невозможен;
- потеря/утечка данных;
- неправильный адресат;
- повторная подача;
- неконтролируемая подпись;
- невозможно сформировать основной документ.

Critical:

- вымышленная норма;
- отмененная норма как действующая;
- нарушение доступа;
- поврежденный документ;
- ложный статус;
- неверная передача обязательных полей.

8. Проверь его тестами и сборкой.
9. Обнови документацию/status.
10. Сделай коммит.
11. Продолжай следующий P0 автоматически.

Не завершай первый запуск сообщением «я изучил проект» или «готов приступить». До первого ответа должно быть выполнено минимум: baseline-аудит, tracking docs и один законченный проверенный кодовый срез, если этому не препятствует реальный внешний blocker.
